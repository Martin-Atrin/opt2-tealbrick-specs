
## connect: connected accounts as a manifest scope type (with per-account tier)
- Need: the general scope mechanism (DECISION-LOG "one GENERAL contract mechanism for app scopes") must let Connect declare scope type `account` whose instances are created at run time inside Connect (not in Portal). A scope instance = `{type:"account", id, label, service, kind:"as_me"|"as_itself"}`.
- Each account scope carries a per-account tier: `read` | `read_update` | `read_update_delete` (PRD glossary "Tier"). The tier is set in Connect (the app is the authority); the canvas line only shows a summary ("2 accounts: Gmail x2 READ").
- Ask: how the grant names scopes. Proposal: the canvas edge grants only "agent may use Connect" (CRUD class on Connect's operations); per-account tier lives in Connect's own store and is enforced by the SDK authorization function as a second check (grant CRUD ∩ account tier). Alternatively the grant token lists `scopes:[{type:"account",id,tier}]` pushed via bridge config pull. Pick one; Connect needs to know which side is truth.
- Ask: SDK hook for "scope summary" (app → Portal, via bridge) so the canvas line can render the summary without Portal holding account data. Summary must contain no third-party identifiers beyond a label the owner typed.

## connect: operation effect mapping for third-party tools (tier gate)
- Need: Connect proxies thousands of dynamic tools (Composio toolkits, custom MCP servers, Company Box OpenAPI ops). They are not individually in the manifest. - Mapping proposal: read→READ, write+outward→READ_UPDATE, destructive→READ_UPDATE_DELETE; money→always held.
