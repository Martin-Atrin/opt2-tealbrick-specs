## BLOCKER (fix before freeze)

**B1 · PORTAL-API §5.5 `instances.deploy` + §5.6 + CORE §9: J1 "authorise agent" happens before a bridge exists.** The bridge is deployed only with the first app ("bridge auto-deployed with the first app"; `DeployResult.bridge.deployedNow`). J1 order is Railway → add agent → **authorise** → search → deploy Knowledge. Authorise needs the bridge in both paths. K2b has `aud = tb:brg:<id>` and `PairingCode.mcpUrl`. The Claude/Codex connector URL is the bridge. Device-flow `scope=agent` returns `mcp_url`, and K5 comes from the bridge. The first app's popup Keys step also gets `409 bridge_not_ready`, so J1 "add keys in the popup" breaks. Fix: deploy the bridge when `workspaces.set_infrastructure` succeeds (onboarding step 1). Add phase `bridge` to that op, or add one op `bridge.deploy` (B, draftable) with SSE progress. Remove "deploys with your first app" from `instances.deploy`/`keys.status`.

**B2 · routes.ts `device.requests_list` / `device.approve` + CREDENTIALS §6: device requests are unbound and can be approved by id.** `device.start` is public and binds no account. `DeviceRequestListInput.userCode` is optional, so the list can return every pending request on Portal. `device.approve {dev}` approves by id and needs no proof that the person holds the user code. An attacker can start a `scope=owner` flow, wait for any owner to click it, and get that owner's K3. Also `DeviceRequest.userCode` is returned in clear, but CREDENTIALS §6 stores only a digest of it. Fix: remove the unfiltered list. Make `userCode` required: a lookup returns one request. `device.approve` takes `{userCode, ws?, agt?}` (digest match, 5 tries/10 min already specified). The J1 "one click" stays: TBD/CLI opens `verification_uri_complete`. Drop `userCode` from `DeviceRequest`. Add conformance cases.

**B3 · types/credentials.ts `DEVICE_FLOW` + K2 row `holderDetail: "owner CLI / TBD / kit (scope owner)"` + routes.ts `DeviceStartInput`: an agent runtime can obtain a person credential.** `kit` runs inside Claude Agent SDK/Eve agents. The types allow `client_id: kit, scope: owner`, and that gives K3. This breaks PRD §4 and R-P1 ("must be impossible by design"). PORTAL-API §5.4 says owner = `tealbrick-cli|tbd`, but the types do not enforce it. Fix: make `DeviceStartInput` a discriminated union. `{scope:"owner", client_id:"tealbrick-cli"|"tbd"}` has no key. `{scope:"agent", client_id, public_key (required), harness, agt?}`. Core refuses other combinations. Use two approval screens with different wording; the owner screen says "this signs in a tool AS YOU — never approve for an agent". Add conformance case `cred.p1.kit_cannot_get_owner`.

**B4 · CREDENTIALS §12, §9.4, §18 R-owner-draft, "Noted risk", K3 row vs PORTAL-API §1.2 + routes.ts `tickets.launch` (auth `B` only) vs SDK-API §4.5: three answers to "can TBD's K3 get launch tickets?".** CREDENTIALS says yes (and records the risk that a TBD-side process can approve holds/edit scopes without a browser). PORTAL-API and SDK-API say never. Fix: adopt the SDK-API/PORTAL-API answer. K3 never obtains any K11, and TBD opens Portal launch in the system browser (K1). Delete the noted risk. Fix the K3 row, §9.4, §12, R-owner-draft and `types/credentials.ts` audienceRule.

**B5 · BRIDGE §8.1 ("bridge-only SDK calls … carry a hook-style proof without a grant") vs CREDENTIALS §10 + types/credentials.ts `CallProofClaims` + SDK-API §3.2: the proof for catalog / resolve / mark / `tb.scope_summary` is undefined.** Only op and hook proofs exist. A hook proof needs `hook` declared in the app's own manifest, so it cannot be used. No SDK route serves `tb.scope_summary` without a grant. Bridge and SDK teams build these in parallel in P1. Fix: add a third `tb-call+jwt` variant `CallProofBridgeOpClaims {call, bop: "catalog"|"resolve"|"mark"|"scope_summary", op?, in?}`. Add `verifyBridgeOpProof` to the manifest package. Add `POST /tb/v1/bridge/scope-summary` (or name the route) to SDK §3.2.

**B6 · Wire shapes that disagree (markdown vs types; types vs schema).** (a) Owner device-token result: CREDENTIALS §6 `{access_token, token_type, expires_in}` vs routes.ts `{scope, session_token, session_id, expires_at}`. (b) Agent result: CREDENTIALS §6 `{con, agt, ws, bridge_url}` vs routes.ts/CLI §4 `{connection_id, agent_id, workspace_id, mcp_url, token_endpoint}`. (c) CLI §3/§4/§9 send `purpose: owner_session|agent_key`, `client: cli`, `clientName`; routes.ts takes `client_id`, `scope`, `machine_label`. (d) sdk.ts `InstanceSliceBody.revision` vs instance-slice.schema.json `rev`. (e) CORE §5 K2 lists no `kit`-owner case, but credentials.ts does (see B3). Fix: routes.ts is the one source for device-flow wire. CREDENTIALS §6 and CLI quote it by type name and do not restate fields. Rename sdk.ts `revision` → `rev`.

**B7 · BRIDGE §11 + §3.1 `/admin/v1/*` + CREDENTIALS §17 + CLI `tealbrick admin`: standalone turns the bridge into a mini-Portal.** The admin surface covers agents, connections, edges, policy, pause, hook enable, pairing codes, launch/keys tickets and enrol codes. The bridge also becomes the signer of slices, grants, K2b and K11, and "S2 authoritative (edited only by admin ops)". This contradicts §1.2: "S2 = last good config (verified JWS, verbatim)". This grows the bridge past "small" (task item d) and is not needed for "production grade". PRD §3.8 asks only "becomes its own issuer; apps keep working". Fix (cut): the final config is frozen. The bridge re-mints grants and slices from it and signs them with K7. Admin is limited to 4 ops: pause/resume agent or workspace, revoke connection, launch ticket, keys ticket. Adding agents, edges or apps after leaving = next wave. Add the new S9 "self-issued config + owner keys" to the §1.2 inventory. Add conformance for the handover (see S11).

**B8 · routes.ts `instances.register_own_infra` (`idempotent: true`, output `EnrolmentCode`) + PORTAL-API §1.5: Core's idempotency store keeps the raw K6 for 24 h.** "Core keeps (principal, opId, key) → response". The response holds the one-time code in plaintext, which fails the checklist line "codes stored as digests". Fix: set `idempotent: false` (like `bridge.enrolment_code`), or rule that responses of `bodyLog: none` rows are never stored (replay → `409 idempotency_conflict`).

## SHOULD (v0.1 during P1, no contract break)

- **S1 · CLI §1, CREDENTIALS §12 (task item e):** K3 sits in a keychain item that any process of the same OS user can use through `tealbrick`. On an FDE machine where agents have a shell (Claude Code), every agent can run owner commands. PRD: "agents never get access to that CLI session". Fix: state the boundary (OS user) and keep K3 harmless: reads + drafts only, no codes or tickets in any K3-readable output (true today, so make it a route-table check). Use a keychain ACL with user presence where the OS supports it. Lower idle time from 7 d to 24 h. `tealbrick login` warns when agent items exist on the machine.
- **S2 · SDK-API §4.5, PRD §5 "approvals miniapp / TBD default":** nothing tells the owner that a hold waits. Holds are visible only inside each app's UI, and there is no feed. Fix (Coordinator call): add `pendingHolds: n` per `ins` (count only) to `StatusReport` → badge on the canvas node → double-click opens Holds. TBD shows the same counts.
- **S3 · BRIDGE §6.2 path A/B, PORTAL-API `pairing.connect_request`:** OAuth consent phishing is possible. An attacker's DCR client starts authorize at the owner's bridge and sends the owner the approve link. Fix: the approve screen shows the `redirect_uri` host and marks the DCR `client_name` "unverified". State that Core checks bridge.ws.account = principal (these paths have no `{ws}`).
- **S4 · CLI §3.2/§4, PORTAL-API §7 J3:** 15–16 agents means 16 separate device flows and 16 browser approvals. That conflicts with "connecting must be very easy". Fix: one `scope=agent` device request may carry up to 64 `{agt, public_key}` pairs (one machine); one approval screen, one click.
- **S5 · CORE I8, CREDENTIALS §11:** companion grants do not specify `held` / `caps`. An app→app outward call (e.g. a send) can run with no hold. Fix: companion grants carry `held` = the workspace default held families and no caps; `money` is always held.
- **S6 · MANIFEST §7 ("Core … delivers [settings] in the instance slice") vs instance-slice.schema.json (no `settings`):** the schema wins. Fix the text: settings reach the app only as env at (re)deploy; `instances.update {settings}` redeploys.
- **S7 · BRIDGE §1.2/§12:** no backup is specified for the bridge volume. HA "standby from the latest volume backup" assumes one exists. Losing it means all keys are re-entered and all pairing harnesses re-pair. Fix: use the Railway volume backup of the bridge service, add a restore test (PRD §11), or explicitly accept the loss.
- **S8 · BRIDGE §7.4 skill sanitizer (task item d):** content filtering in the bridge. Fix: sanitize once in `validateAppFiles` (CI) and in Core's render (owner overrides). The bridge only substitutes `{{agent.*}}`.
- **S9 · CORE §9, CREDENTIALS §7 path C/§8, CLI §4 `agent login --code` (task item f):** a second way for the CLI to connect an agent. It needs a custom grant type `urn:tealbrick:…:pairing`. K2 and K2b then both serve "CLI agent login", which fails the checklist line "no purpose served by two kinds". Fix: cut path C; the CLI always uses the key connection.
- **S10 · BRIDGE §7.4 (J1 "skills pushed"):** delivery relies on MCP resources + `initialize.instructions`, which Claude Desktop/Codex may not inject. Fix: run a P1 probe per tested harness. Fallback: one read tool `<product>__tb_skills` listed in tools/list.
- **S11 · CONFORMANCE:** cases missing for leaving-Portal handover (apps accept bridge-issued grants, Portal keys untrusted), device binding (B2/B3), pairing path A `ret`/state checks, `dynamic_ceiling_exceeded`, `hook_reentry`/`call_depth_exceeded`, `slice_stale`, post-approval retry (SDK §4.3). Open Q2 defers SDK-function coverage, which fails the checklist line "every SDK function covered". Fix: list the cases now. Generate the SDK list from `types/sdk.ts` at freeze, not at P1.
- **S12 · REPOS §3:** "conformance ── … miniapp-sdk, bridge" makes a repo cycle (-sdk → -bridge → -sdk). It also tests the bridge with the bridge, which contradicts CONFORMANCE §3 ("fakes generated from spec"). Fix: conformance imports spec + manifest only.
- **S13 · CREDENTIALS §13 vs PRD §4 "pause applies to every credential that can reach an app":** launch/keys tickets are not paused, and companion calls continue for work a paused agent started. Both are reasonable. Fix: record Coordinator acceptance as a C-decision, so QA does not file them as defects.
